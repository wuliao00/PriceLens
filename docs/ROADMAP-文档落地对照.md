## 七、明确不做的与原因

- **模块化重构（§架构）**：单模块规模下收益低、风险高（要动全部 Room 迁移与门禁），不做。
- **图表库替换**：自绘 Canvas 已满足需求，换库收益不抵重做成本，不做。
- **规则化数据源 / 社区 Discussions**：都依赖 §三 的规则基建与运营，单独立项。
- **ACRA 崩溃收集**：需要自托管后端（文档给了 Cloudflare Worker 方案）。在你有后端之前，
  建议先做"纯本地崩溃日志导出"（复用现有 LogT 落盘 + 导出分享），**需你拍板**。

### 9.5 第四批之二（2026-10-03 晚）——设计债落地：令牌化、自适应布局、桌面端字号收口

承接 §9.4 的"僵硬化"批评，这一批做的是**能被测试钉住的**那部分，做不到的地方写清楚为什么不做。

**一、浮窗尺寸从"两文件各写一份"变成一个真相源（`OverlayMetrics.kt`）**
最实的债不是颜色，是跨文件一致性只靠注释维持：`OverlayManager` 写 `PANEL_MAX_WIDTH_DP = 304f
// = widthIn(max = 280.dp) + 左右各 12dp`，而 280 和 12 在 `PriceOverlay` 里各写一遍。
改 UI 的人看不见那条注释 ⇒ 窗口仍按 304 算，面板右边缘被**静默裁掉**，且只在数据最长时露出来。
现在关系是函数（`panelWindowMaxWidthDp()`），`OverlayMetricsTest` 里先钉等值（304/60/24 一个都没变，
证明这只是搬家），再钉不变量：`60..2000dp` 每一档都断言"面板+外圈不得超过窗口""胶囊不得比面板宽"。
胶囊圆角也改成 `capsuleCornerDp() = 高度 / 2`，pill 形不可能再被写死成 24。
`PriceOverlay` 的 29 处裸 dp 与 2 处裸时长一并归口（`Elevations.OverlayTonal/Capsule/Panel`、
`MotionDurations.ShimmerSweep/PriceRoll/Standard`）；`AnimatedVisibility` 不再吃系统默认时长。
变异自证：把两处 `minOf` 上限摘掉 ⇒ 恰好 3 条用例红（panel / capsule / invariants），其余仍绿。

**二、自适应布局有了第一版分档（`ui/layout/Adaptive.kt`）**
全仓 `WindowSizeClass` 出现 0 次是这次审计查出来的事实：折叠屏展开、平板、分屏下 App 用的还是手机排版。
分档下界用 Material 3 官方的 600dp / 840dp，**不是我自己调的数**（这正是"别僵硬化"要的做法：
引用现成标准而不是照着手里的样本凑阈值）。消费方式保守：COMPACT 返回 `null`（不是"一个大数"，
因为 `widthIn(max = 很大)` 与"不挂这条 modifier"在 Compose 里不等价），保证 360~500dp 的手机
与改造前逐像素一致；MEDIUM 限宽 600dp、EXPANDED 限宽 840dp。
（**更正**：这里原先写的是"限宽…居中"。真机复测证明**只有"限宽"成立**——列宽确实是 600dp，
但整列仍贴左。居中属于接线侧的修饰符顺序问题，与分档本身无关，取证与修法见 §9.8。）
`AdaptiveTest` 里"主流手机宽度全部留在 COMPACT"是这条改动**不许动手机形态**的钉子。

**三、小组件按高度决定行数（`WidgetLayout.kt`）**
`SizeMode.Exact` 早就开了，但内容是**三行写死**：拖成 2x1 时第三行被窗口裁半截，拖大是一片空白。
现在行数由 `rowsFor(heightDp)` 算，阈值从"内边距 12dp ×2 + 一行 16sp 粗体 24dp"派生（同
`RowBudget` 的写法：可查的数推出来的，不是拍的）。`android:minHeight=110dp` 那条 4x2 承诺代入
⇒ 仍然 3 行，所以已验收的默认尺寸零变化；读不到尺寸（`Dp.Unspecified`=NaN）时回默认 3 行而不是猜。
变异自证：`>=` 写成 `>` ⇒ 边界用例当场红。

**四、桌面端字号令牌收口**
`components.css` 里 5 个裸 `font-size`（16/18/20/24/40px）原先游离在 `--fs-*` 五档之外——
调字阶的人改 tokens 看不见它们，等于两套字号真相。新增 `--fs-hero/amount/price/subtitle` 四档
（值照搬，不改观感）并全部换成 `var()`；脚本核过：60 个定义、52 个引用、**没有一个引用指向未定义变量**，
新加的四档各自"定义 1 次、引用 1 次"（不留没消费者的令牌）。
`@media` 断点这一批**没加**，理由是可查的：Electron 主窗口 `minWidth: 760`（`src/main/index.js`），
窄于 760 的场景根本到不了，最窄时内容区仍有 760−200(侧栏)=560px；在没有可视验证手段之前，
为了"看起来自适应"塞断点是加分歧不是减风险。

**五、两条审计项核实后否掉，没有动手**
- "球上是裸『收』字要换成图标"：当时 grep 到 `ovl_ball_collapse=「收起」` 两个字，就判这条审计不成立——
  **这个"核实"本身是错的**。23:46 真机截图打脸：折叠胶囊上实际只剩「页面价 ¥11,579」+「收」，
  「起」和右边那枚 × 都被裁到胶囊外。原因不是文案，是**宽度分配**：胶囊宽被
  `min(280, 屏宽×0.4)` 卡住，价格文本按固有宽度先站满，两个动作就被挤出去。
  已改成价格文本 `weight(1f, fill = false)`（宽度不够时先缩价格、宁可省略号，
  也不许把动作挤没）。**教训：字符串资源里有两个字，不等于屏幕上看得见两个字。**
  审计项的"核实"必须落到渲染结果（截图/dump），grep 只能证明源码里写了什么。
- "吸边动画"：小圆球拖拽手感是用户本人 13:45 在 PLB110 上刚复验通过的，而这一刻 `adb devices` 是空的，
  改完无法验手感 ⇒ 按"不许把没验过的东西写成完成"留着。

**没做到的（如实记）**：以上分档与限宽的**接线部分（MainActivity / WatchWidget 的 Compose 侧）没有测试覆盖**——
纯函数测的是判据，判据接到底层树之后长什么样，本机既起不了模拟器（无 hypervisor）也没有连着的大屏设备，
看不到。`npm run lint` 也不校验 CSS 令牌。这一条与任务 #53 是同一件事，等用户那台平板模拟器起来再补渲染证据。

### 9.6 第四批之三（2026-10-03 深夜）——adb 走查又抓到标题链三层误杀 + 找券三版并行开工

**一、真机当场又抓到一次"把促销语当商品名"，而且和前三次不同因。**
用户说"手机连回来了、不要模拟器"之后，我装了一版 `.dev` 走京东商详，logcat 直接抓到：

    A11Y 命中来源=规则命中 规则 jd@v4/product_detail [title=textRegex:^[^¥￥]{10,200}$ …]
      title=当前地区可领，本单可减1500元
    搜索开始: [当前地区可领，本单可减1500元]   → 当当 / 什么值得买 / 识货 各拉一次

同一帧上真商品名是 145 字的 `雷神（ThundeRobot）猎刃S 电竞游戏本…`。修的过程一共挖出**三层**，
每单独修一层都救不回来（我前两次就是这么以为"已修"的）：
1. 规则兜底网 `^[^¥￥]{10,80}$` 把 145 字排除在网外 ⇒ 网里只剩那条 17 字促销行；抬到 200；
2. 网抬上去之后规则**仍然**给促销行，因为选择器返回的是 **BFS 里第一个命中**：
   促销行在 depth=8、真名在 depth=23 ⇒ `title` 字段改成取全树 `titleScore` 最高者
   （严格大于，平手仍按树序）；**其余字段保持"先出现的那个"** —— price/buyNow 的语义就是页面上
   第一个，改成最高分反而会把划线价与到手价混掉；
3. 规则这次真取到了 145 字，却被 `isPlausibleTitle` 里 `if (strict) 80 else 120` 又判死
   ⇒ 上限收成**一个**常量 `TITLE_MAX_LEN = 220`，两路共用。
   六棵真机树商品名实测 32 / 61 / 145 / 170 —— 120 和那个 80 是同一种错：**照着手里的样本凑上限**。
另加一条形状判据：迷你沉浸页的媒体角标 `1个视频，4张图片` 也曾被当商品名送去搜索；
判据是"数字+短非数字段、逗号串起来、≥2 段"的计数枚举（不是词表），
并配三条 positive control 钉住不许误杀（`500ml 2瓶 酱香型白酒` / `泸州老窖 窖龄30年，52度 500mL 6瓶` / `240Hz高刷`）。
新增第五棵真机夹具 `jd_detail_guobu_popup_plb110_20261003.xml`（212 节点）。规则版本自动递增到 4。

**二、浮窗令牌化的真机几何对照（§9.5 欠的那条渲染证据，手机补上了）。**
同一台 PLB110、同一个京东商详页、同一枚折叠胶囊：
正式包 2.8.0.1（旧代码）`Requested w=587 h=252`，`.dev` 新代码 `Requested w=588 h=252`，
`mAttrs={(32,200)(wrapxwrap) gr=TOP END CENTER ty=APPLICATION_OVERLAY}` 逐字相同。
那 1px 差是**四舍五入发生的位置不同**：旧写法 `screenWidthDp * 0.4f` 直接进 `.dp`（143.6dp→502.6px），
新写法先 `roundToInt` 再乘（144dp→504px）。方向上新写法更干净（先取整再换算，窗口尺寸不随 density 抖动）。

**三、规则通道在真机上确认打通**：`.dev` 冷启动日志
`RULES 本地装载 builtin=[jd] disk=[jd] 生效=[jd@v4]`（v3 那次为 `jd@v3`），
且 `启发式回落（规则未命中，词表=规则 gate）` 这条日志证明 §9.5 的 gate 通道真的在跑。
Gitee raw 侧也核对过：`manifestVersion=2026100302`、`jd@v3`、文件 sha256 与清单一致。

**四、找券改成一条流水线，三版并行开工（分支不是版本，合完才定版本号）。**
用户给的诊断我接受其中一条硬的：**三个入口都错 ⇒ 病根不在适配器，在没有统一槽位定义**。
所以拆成四路并行（每路一个 ASCII 工作树 + 一份台账，构建全走同一把全机锁）：

### 9.7 第五批（2026-10-04 凌晨）——两个"会把对的实现判成失败"的静默坑

这一节记的不是功能，是**量具与优先级**的坑。它们共同的形状是：现象指向"代码没修好"，
真因却在修好之后的某条链路上。下次遇到"改了却没生效"，先把它当**候选成因**而不是结论。

**坑一：远端规则包覆盖内置资产时不比版本号，`v3` 会把新 APK 里的 `v4` 原样盖掉。**

`RuleMerge.effective(high, low)` 的优先级是"远端 > 磁盘缓存 > 内置"（`RuleMerge.kt:12-18`），
同 id 直接 `putAll` 覆盖——**没有"版本号更高才覆盖"这一条**。这条设计本身是对的：
规则下发要能回滚（远端推一个更低的版本就得生效，否则坏规则撤不掉）。
但它的副作用直到这次才撞上：e81a517 把标题修复同时写进代码与规则包，内置资产升到 `jd@v4`，
而 **Gitee 上还是 `jd@v3`**（main 还没合这批提交）。于是新 APK 装到手机上，
只要设备能同步到远端，跑的就是 v3 的规则内容——真机走查会看见"标题还是被促销行占了"，
而代码与内置资产明明都是对的。**症状指向"修复无效"，真因是远端比内置旧。**

处置：main 快进到 4404b50（含规则 v4）→ 推 gitee main（`84c25f0..4404b50`，非强推）→

jd.json 实际字节的 sha256 与清单声明**自洽**。顺带一条环境事实：Gitee raw 现在 302 到
`raw.giteeusercontent.com`，不带 `-L` 会拿到那段 HTML 跳转体并误判成"内容坏了"。

诚实边界：远端与内置现在是**同版本同 sha**，所以真机上的"生效=[jd@v4]"只能证明
"跑的是 v4 内容"，**不能单独证明远端那条同步链路走通了**。链路本身的证据属于更早那次
v2→v3（远端与内置不同版，才分辨得出是谁在生效）。要把这条重新变成可分辨的，
得等规则包真的再进一版。

**坑二：子代理用 Python 镜像仿真出来的"全绿"，不等于 Kotlin 能编译。**

### 9.8 第五批之二（2026-10-04 凌晨）——真机把"我以为修好了的居中"又判了一次

**一、居中这条修了两版，前两版都是错的，第三版才有证据。**
同一台 PLB110、同一个 `wm density 280`（窗口 1256px ⇒ 717dp ⇒ MEDIUM 档，限宽 600dp = 1050px）：

| 写法 | 量到的内容列 bounds | 结论 |
|------|---------------------|------|
| `widthIn → fillMaxHeight → wrapContentWidth`（8cc2a44 之前） | `[0,252][1050,2592]` | 限宽成立、贴左 |
| `wrapContentWidth → widthIn`（**8cc2a44 自称的修复**） | `[0,252][1050,2592]` | **一模一样，还是贴左** |
| `fillMaxWidth → wrapContentWidth → widthIn`（dab1020） | `[103,...][1153,...]`，左右余量各 103px | 居中成立 |

根因：`wrapContentWidth(align)` 是"把内容包紧，再在**自己占到的宽度**里对齐"。没有谁逼它占满父宽时，
它占到的就等于内容宽 ⇒ 对齐量恒为 0。`fillMaxWidth()` 先撑到父给的最大宽，后面才有 206px 可以分。
这条在 8cc2a44 的提交信息里被我写成"顺序反过来就对了"，**而且写进了代码注释**——
一个自信的错注释比没注释更贵：下一个改这里的人会照它再错一遍。现在注释里放的是上面这张表。

EXPANDED 档也顺手量了：`wm density 200` ⇒ 窗口 1004dp ⇒ 限宽 840dp = 1050px，
同一份 dump 按 840dp@200dpi 口径判 ⇒ `left=103 / right_margin=103`。
（这里有个巧合要写明白：600dp@280dpi 与 840dp@200dpi 都等于 1050px，所以量具必须**显式传档**，
用默认参数会"碰巧对"——把 `measure_centering.py` 按 600dp@200dpi 判同一份 dump 就会报出
"居中不成立"，因为它挑中的是另一个 750px 节点。）

**四、浮窗两条 CTA 并排会把中文文案折成"识别到标 / 题 · 点击"。**

**五、回到真机原生分辨率，才发现 b1b9c8f 那次"胶囊挤压修复"只是把病灶换了个位置。**
上面第三、四条的取证全在 `wm density 280`（717dp 窗口）下做，胶囊在那里是**正常**的。
把设备恢复成原生 560dpi（360dp 手机本档）再进同一条商详页，实拍 `shots/detail_after_back.png`：
胶囊里价格那格被挤成一个 **"…"**，只剩「收起 ×」两个动作。
成因链完整摊开是这样：
1. 折叠胶囊宽度上限的老规则是 `min(280dp, 屏宽 × 0.4)` —— 那个 **0.4 是当年随手写的凑数比例**，
   在 360dp 上把胶囊压到 144dp；
2. 而"页面价 ¥11,579 + 收起 + ×"实际需要 ~200dp；
3. b1b9c8f 给价格 `weight(1f, fill = false)` 是为了"宽度不够时先缩价格，别把按钮挤出可视区"——
   它确实保住了按钮，但也让价格**可以被缩到零**，于是症状从"按钮被裁"变成"价格变省略号"；
4. 最扎心的是这条在 CI 与本地门禁里都是**绿的**：`OverlayMetricsTest` 当年把
   `capsuleMaxWidthDp(360) == 144` 当成期望值钉住了。**测试钉住的正是病灶本身。**

处置：折叠态与展开态**共用同一条宽度上限**（`capsuleMaxWidthDp` 直接委托 `panelContentMaxWidthDp`），
0.4 那个比例删掉；测试改成钉"360dp 拿到 280、240dp 窗口跟着收到 216、两态永远相等"。
连带一条纪律：**响应式规则不许只在伪报的大分辨率下看过**——那正好掩盖手机本档；
以后凡是改 `*MaxWidthDp` 这类按窗口宽走的判据，必须"原生档 + 伪报档"各拍一张。

### 9.9 第六批（2026-10-04 凌晨）——找券三版落地，以及"控制面接手"抓出的两条真缺陷

四路并行（core / eval / ui / ai-policy）全部收口。**分支不是版本**，版本号等用户定。

**一、V1 理解层的形状（`com.pricelens.coupon`）**
- `Extraction.coupons: List<CouponSlot>` 与 `Extraction.price: PriceSlots` **分属两个类型** ——
  "到手价被当成券面额"这类错从类型上不可能再发生，这是治"金额槽位混淆"的正解，
  比再加十条词表都管用。
- `AmountRole.of` 只看**数字之前、离数字最近**的词，同下标取长词（`无门槛` 压 `门槛`）；
  判不出返回 null，**绝不默认 DISCOUNT**。
- 状态/范围按词表判，判不出是 UNKNOWN（不许默认 CLAIMABLE / SHOP）；
  优先级把强信号（售罄/过期）排在弱信号（`立即领`）之前。
- 三入口产出同一类型，`nodePath` **只有 PAGE_NODE 入口非空** —— 这个不对称本身就是
  "三入口确实走同一条流水线"的反证材料。
- 词表全部可被远端规则包整体覆盖（含宿主前缀表 `platformPrefixes`）：
  接一个新电商宿主 = 推一条规则，不是发一次版。

**二、两棒子代理都在 150 轮上限被打断，控制面接手时抓出的不是"语法错"而是两条真缺陷**
| 缺陷 | 怎么暴露的 | 为什么它一直没被发现 |
|------|-----------|---------------------|
| `AmountRole.of` 不限量"角色词与数字之间隔了多远" ⇒ `…满199减20 券码：ABCD1234` 里的 1234 被 20 多字之前的 `减` 认领，**凭空多出一张 ¥1234 的券** | 我把 `slots.single()` 换成带消息的 `oneSlot()`，一次红就把两张券的字段打全了 | `single()` 只说 "List has more than one element"，看不出多出来的是什么；而多出来的券带着**正确的** scope/state，看起来像真券 |
| `CouponSlot` 没有 `sourceText` ⇒ "这条不对"导出写不出与 `tools/golden/coupons.jsonl` 同格式的 JSONL | 写 #56 的导出前先读 golden 格式，发现第一字段就是原文 | 理解层自己不需要原文也能跑；断的是**下游复盘能力**，不在同一层就看不见 |

**三、这批最贵的一课：判据里的标点必须走生产路径测。** 第一版 `subsidy-tail` 的间隙写成
"排除全角标点"（`[^，。；、\d]`），单测在 consume 层喂全角句子全绿；而生产路径经
`PostAdapter.normalize` 会把**全角逗号换成半角**，于是 `活动售价3499元,参与补贴…` 里的半角逗号
成了合法间隙 ⇒ 3499（**售价**）被认领成一张 ¥3499 的券，同时 list 槽静默变空。
是**全量评测**（FP 从预期 1 变成 2）抓住的，不是单测。两处一起修：
① 间隙类改**正向汉字类**（`[\u4e00-\u9fa5]{0,4}?`，对标点归一化天然免疫，空格也不许进——
这里的空格多半是节点拼接留下的）；② 管线加"**价格角色优先**"：尺子在数字左侧认出 售价/原价/到手/
券后/降 这类词时，模板不许把它改成券 —— 这正是 PLB110 上"模型把 5998 写成门槛"的同一个坑，
这次是我自己踩的。新增的生产路径钉子：`CouponPipelineTest.售价数字走生产路径也不许变成券面额`
（走 `CouponExtractor.fromPost`，而不是只喂 consume）。

跑一次全量 eval）；1.7B 模型这条路仍未试（§9.11 的结论没变：0.6B 的提示词杠杆已经到底）。
