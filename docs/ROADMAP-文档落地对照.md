## 七、明确不做的与原因

- **模块化重构（§架构）**：单模块规模下收益低、风险高（要动全部 Room 迁移与门禁），不做。
- **图表库替换**：自绘 Canvas 已满足需求，换库收益不抵重做成本，不做。
- **规则化数据源 / 社区 Discussions**：都依赖 §三 的规则基建与运营，单独立项。
- **ACRA 崩溃收集**：需要自托管后端（文档给了 Cloudflare Worker 方案）。在你有后端之前，
  建议先做"纯本地崩溃日志导出"（复用现有 LogT 落盘 + 导出分享），**需你拍板**。

### 9.5 第四批之二（2026-10-03 晚）——设计债落地：令牌化、自适应布局、桌面端字号收口

承接 §9.4 的"僵硬化"批评，这一批做的是**能被测试钉住的**那部分，做不到的地方写清楚为什么不做。

**一、浮窗尺寸从"两文件各写一份"变成一个真相源（`OverlayMetrics.kt`）**
最实的债不是颜色，是跨文件一致性只靠注释维持：`OverlayManager` 写 `PANEL_MAX_WIDTH_DP = 304f
// = widthIn(max = 280.dp) + 左右各 12dp`，而 280 和 12 在 `PriceOverlay` 里各写一遍。
改 UI 的人看不见那条注释 ⇒ 窗口仍按 304 算，面板右边缘被**静默裁掉**，且只在数据最长时露出来。
现在关系是函数（`panelWindowMaxWidthDp()`），`OverlayMetricsTest` 里先钉等值（304/60/24 一个都没变，
证明这只是搬家），再钉不变量：`60..2000dp` 每一档都断言"面板+外圈不得超过窗口""胶囊不得比面板宽"。
胶囊圆角也改成 `capsuleCornerDp() = 高度 / 2`，pill 形不可能再被写死成 24。
`PriceOverlay` 的 29 处裸 dp 与 2 处裸时长一并归口（`Elevations.OverlayTonal/Capsule/Panel`、
`MotionDurations.ShimmerSweep/PriceRoll/Standard`）；`AnimatedVisibility` 不再吃系统默认时长。
变异自证：把两处 `minOf` 上限摘掉 ⇒ 恰好 3 条用例红（panel / capsule / invariants），其余仍绿。

**二、自适应布局有了第一版分档（`ui/layout/Adaptive.kt`）**
全仓 `WindowSizeClass` 出现 0 次是这次审计查出来的事实：折叠屏展开、平板、分屏下 App 用的还是手机排版。
分档下界用 Material 3 官方的 600dp / 840dp，**不是我自己调的数**（这正是"别僵硬化"要的做法：
引用现成标准而不是照着手里的样本凑阈值）。消费方式保守：COMPACT 返回 `null`（不是"一个大数"，
因为 `widthIn(max = 很大)` 与"不挂这条 modifier"在 Compose 里不等价），保证 360~500dp 的手机
与改造前逐像素一致；MEDIUM 限宽 600dp、EXPANDED 限宽 840dp。
（**更正**：这里原先写的是"限宽…居中"。真机复测证明**只有"限宽"成立**——列宽确实是 600dp，
但整列仍贴左。居中属于接线侧的修饰符顺序问题，与分档本身无关，取证与修法见 §9.8。）
`AdaptiveTest` 里"主流手机宽度全部留在 COMPACT"是这条改动**不许动手机形态**的钉子。

**三、小组件按高度决定行数（`WidgetLayout.kt`）**
`SizeMode.Exact` 早就开了，但内容是**三行写死**：拖成 2x1 时第三行被窗口裁半截，拖大是一片空白。
现在行数由 `rowsFor(heightDp)` 算，阈值从"内边距 12dp ×2 + 一行 16sp 粗体 24dp"派生（同
`RowBudget` 的写法：可查的数推出来的，不是拍的）。`android:minHeight=110dp` 那条 4x2 承诺代入
⇒ 仍然 3 行，所以已验收的默认尺寸零变化；读不到尺寸（`Dp.Unspecified`=NaN）时回默认 3 行而不是猜。
变异自证：`>=` 写成 `>` ⇒ 边界用例当场红。

**四、桌面端字号令牌收口**
`components.css` 里 5 个裸 `font-size`（16/18/20/24/40px）原先游离在 `--fs-*` 五档之外——
调字阶的人改 tokens 看不见它们，等于两套字号真相。新增 `--fs-hero/amount/price/subtitle` 四档
（值照搬，不改观感）并全部换成 `var()`；脚本核过：60 个定义、52 个引用、**没有一个引用指向未定义变量**，
新加的四档各自"定义 1 次、引用 1 次"（不留没消费者的令牌）。
`@media` 断点这一批**没加**，理由是可查的：Electron 主窗口 `minWidth: 760`（`src/main/index.js`），
窄于 760 的场景根本到不了，最窄时内容区仍有 760−200(侧栏)=560px；在没有可视验证手段之前，
为了"看起来自适应"塞断点是加分歧不是减风险。

**五、两条审计项核实后否掉，没有动手**
- "球上是裸『收』字要换成图标"：当时 grep 到 `ovl_ball_collapse=「收起」` 两个字，就判这条审计不成立——
  **这个"核实"本身是错的**。23:46 真机截图打脸：折叠胶囊上实际只剩「页面价 ¥11,579」+「收」，
  「起」和右边那枚 × 都被裁到胶囊外。原因不是文案，是**宽度分配**：胶囊宽被
  `min(280, 屏宽×0.4)` 卡住，价格文本按固有宽度先站满，两个动作就被挤出去。
  已改成价格文本 `weight(1f, fill = false)`（宽度不够时先缩价格、宁可省略号，
  也不许把动作挤没）。**教训：字符串资源里有两个字，不等于屏幕上看得见两个字。**
  审计项的"核实"必须落到渲染结果（截图/dump），grep 只能证明源码里写了什么。
- "吸边动画"：小圆球拖拽手感是用户本人 13:45 在 PLB110 上刚复验通过的，而这一刻 `adb devices` 是空的，
  改完无法验手感 ⇒ 按"不许把没验过的东西写成完成"留着。

**没做到的（如实记）**：以上分档与限宽的**接线部分（MainActivity / WatchWidget 的 Compose 侧）没有测试覆盖**——
纯函数测的是判据，判据接到底层树之后长什么样，本机既起不了模拟器（无 hypervisor）也没有连着的大屏设备，
看不到。`npm run lint` 也不校验 CSS 令牌。这一条与任务 #53 是同一件事，等用户那台平板模拟器起来再补渲染证据。

### 9.6 第四批之三（2026-10-03 深夜）——adb 走查又抓到标题链三层误杀 + 找券三版并行开工

**一、真机当场又抓到一次"把促销语当商品名"，而且和前三次不同因。**
用户说"手机连回来了、不要模拟器"之后，我装了一版 `.dev` 走京东商详，logcat 直接抓到：

    A11Y 命中来源=规则命中 规则 jd@v4/product_detail [title=textRegex:^[^¥￥]{10,200}$ …]
      title=当前地区可领，本单可减1500元
    搜索开始: [当前地区可领，本单可减1500元]   → 当当 / 什么值得买 / 识货 各拉一次

同一帧上真商品名是 145 字的 `雷神（ThundeRobot）猎刃S 电竞游戏本…`。修的过程一共挖出**三层**，
每单独修一层都救不回来（我前两次就是这么以为"已修"的）：
1. 规则兜底网 `^[^¥￥]{10,80}$` 把 145 字排除在网外 ⇒ 网里只剩那条 17 字促销行；抬到 200；
2. 网抬上去之后规则**仍然**给促销行，因为选择器返回的是 **BFS 里第一个命中**：
   促销行在 depth=8、真名在 depth=23 ⇒ `title` 字段改成取全树 `titleScore` 最高者
   （严格大于，平手仍按树序）；**其余字段保持"先出现的那个"** —— price/buyNow 的语义就是页面上
   第一个，改成最高分反而会把划线价与到手价混掉；
3. 规则这次真取到了 145 字，却被 `isPlausibleTitle` 里 `if (strict) 80 else 120` 又判死
   ⇒ 上限收成**一个**常量 `TITLE_MAX_LEN = 220`，两路共用。
   六棵真机树商品名实测 32 / 61 / 145 / 170 —— 120 和那个 80 是同一种错：**照着手里的样本凑上限**。
另加一条形状判据：迷你沉浸页的媒体角标 `1个视频，4张图片` 也曾被当商品名送去搜索；
判据是"数字+短非数字段、逗号串起来、≥2 段"的计数枚举（不是词表），
并配三条 positive control 钉住不许误杀（`500ml 2瓶 酱香型白酒` / `泸州老窖 窖龄30年，52度 500mL 6瓶` / `240Hz高刷`）。
新增第五棵真机夹具 `jd_detail_guobu_popup_plb110_20261003.xml`（212 节点）。规则版本自动递增到 4。

**二、浮窗令牌化的真机几何对照（§9.5 欠的那条渲染证据，手机补上了）。**
同一台 PLB110、同一个京东商详页、同一枚折叠胶囊：
正式包 2.8.0.1（旧代码）`Requested w=587 h=252`，`.dev` 新代码 `Requested w=588 h=252`，
`mAttrs={(32,200)(wrapxwrap) gr=TOP END CENTER ty=APPLICATION_OVERLAY}` 逐字相同。
那 1px 差是**四舍五入发生的位置不同**：旧写法 `screenWidthDp * 0.4f` 直接进 `.dp`（143.6dp→502.6px），
新写法先 `roundToInt` 再乘（144dp→504px）。方向上新写法更干净（先取整再换算，窗口尺寸不随 density 抖动）。

**三、规则通道在真机上确认打通**：`.dev` 冷启动日志
`RULES 本地装载 builtin=[jd] disk=[jd] 生效=[jd@v4]`（v3 那次为 `jd@v3`），
且 `启发式回落（规则未命中，词表=规则 gate）` 这条日志证明 §9.5 的 gate 通道真的在跑。
Gitee raw 侧也核对过：`manifestVersion=2026100302`、`jd@v3`、文件 sha256 与清单一致。

**四、找券改成一条流水线，三版并行开工（分支不是版本，合完才定版本号）。**
用户给的诊断我接受其中一条硬的：**三个入口都错 ⇒ 病根不在适配器，在没有统一槽位定义**。
所以拆成四路并行（每路一个 ASCII 工作树 + 一份台账，构建全走同一把全机锁）：

### 9.7 第五批（2026-10-04 凌晨）——两个"会把对的实现判成失败"的静默坑

这一节记的不是功能，是**量具与优先级**的坑。它们共同的形状是：现象指向"代码没修好"，
真因却在修好之后的某条链路上。下次遇到"改了却没生效"，先把它当**候选成因**而不是结论。

**坑一：远端规则包覆盖内置资产时不比版本号，`v3` 会把新 APK 里的 `v4` 原样盖掉。**

`RuleMerge.effective(high, low)` 的优先级是"远端 > 磁盘缓存 > 内置"（`RuleMerge.kt:12-18`），
同 id 直接 `putAll` 覆盖——**没有"版本号更高才覆盖"这一条**。这条设计本身是对的：
规则下发要能回滚（远端推一个更低的版本就得生效，否则坏规则撤不掉）。
但它的副作用直到这次才撞上：e81a517 把标题修复同时写进代码与规则包，内置资产升到 `jd@v4`，
而 **Gitee 上还是 `jd@v3`**（main 还没合这批提交）。于是新 APK 装到手机上，
只要设备能同步到远端，跑的就是 v3 的规则内容——真机走查会看见"标题还是被促销行占了"，
而代码与内置资产明明都是对的。**症状指向"修复无效"，真因是远端比内置旧。**

处置：main 快进到 4404b50（含规则 v4）→ 推 gitee main（`84c25f0..4404b50`，非强推）→

jd.json 实际字节的 sha256 与清单声明**自洽**。顺带一条环境事实：Gitee raw 现在 302 到
`raw.giteeusercontent.com`，不带 `-L` 会拿到那段 HTML 跳转体并误判成"内容坏了"。

诚实边界：远端与内置现在是**同版本同 sha**，所以真机上的"生效=[jd@v4]"只能证明
"跑的是 v4 内容"，**不能单独证明远端那条同步链路走通了**。链路本身的证据属于更早那次
v2→v3（远端与内置不同版，才分辨得出是谁在生效）。要把这条重新变成可分辨的，
得等规则包真的再进一版。

**坑二：子代理用 Python 镜像仿真出来的"全绿"，不等于 Kotlin 能编译。**

### 9.8 第五批之二（2026-10-04 凌晨）——真机把"我以为修好了的居中"又判了一次

**一、居中这条修了两版，前两版都是错的，第三版才有证据。**
同一台 PLB110、同一个 `wm density 280`（窗口 1256px ⇒ 717dp ⇒ MEDIUM 档，限宽 600dp = 1050px）：

| 写法 | 量到的内容列 bounds | 结论 |
|------|---------------------|------|
| `widthIn → fillMaxHeight → wrapContentWidth`（8cc2a44 之前） | `[0,252][1050,2592]` | 限宽成立、贴左 |
| `wrapContentWidth → widthIn`（**8cc2a44 自称的修复**） | `[0,252][1050,2592]` | **一模一样，还是贴左** |
| `fillMaxWidth → wrapContentWidth → widthIn`（dab1020） | `[103,...][1153,...]`，左右余量各 103px | 居中成立 |

根因：`wrapContentWidth(align)` 是"把内容包紧，再在**自己占到的宽度**里对齐"。没有谁逼它占满父宽时，
它占到的就等于内容宽 ⇒ 对齐量恒为 0。`fillMaxWidth()` 先撑到父给的最大宽，后面才有 206px 可以分。
这条在 8cc2a44 的提交信息里被我写成"顺序反过来就对了"，**而且写进了代码注释**——
一个自信的错注释比没注释更贵：下一个改这里的人会照它再错一遍。现在注释里放的是上面这张表。

EXPANDED 档也顺手量了：`wm density 200` ⇒ 窗口 1004dp ⇒ 限宽 840dp = 1050px，
同一份 dump 按 840dp@200dpi 口径判 ⇒ `left=103 / right_margin=103`。
（这里有个巧合要写明白：600dp@280dpi 与 840dp@200dpi 都等于 1050px，所以量具必须**显式传档**，
用默认参数会"碰巧对"——把 `measure_centering.py` 按 600dp@200dpi 判同一份 dump 就会报出
"居中不成立"，因为它挑中的是另一个 750px 节点。）

**四、浮窗两条 CTA 并排会把中文文案折成"识别到标 / 题 · 点击"。**

**五、回到真机原生分辨率，才发现 b1b9c8f 那次"胶囊挤压修复"只是把病灶换了个位置。**
上面第三、四条的取证全在 `wm density 280`（717dp 窗口）下做，胶囊在那里是**正常**的。
把设备恢复成原生 560dpi（360dp 手机本档）再进同一条商详页，实拍 `shots/detail_after_back.png`：
胶囊里价格那格被挤成一个 **"…"**，只剩「收起 ×」两个动作。
成因链完整摊开是这样：
1. 折叠胶囊宽度上限的老规则是 `min(280dp, 屏宽 × 0.4)` —— 那个 **0.4 是当年随手写的凑数比例**，
   在 360dp 上把胶囊压到 144dp；
2. 而"页面价 ¥11,579 + 收起 + ×"实际需要 ~200dp；
3. b1b9c8f 给价格 `weight(1f, fill = false)` 是为了"宽度不够时先缩价格，别把按钮挤出可视区"——
   它确实保住了按钮，但也让价格**可以被缩到零**，于是症状从"按钮被裁"变成"价格变省略号"；
4. 最扎心的是这条在 CI 与本地门禁里都是**绿的**：`OverlayMetricsTest` 当年把
   `capsuleMaxWidthDp(360) == 144` 当成期望值钉住了。**测试钉住的正是病灶本身。**

处置：折叠态与展开态**共用同一条宽度上限**（`capsuleMaxWidthDp` 直接委托 `panelContentMaxWidthDp`），
0.4 那个比例删掉；测试改成钉"360dp 拿到 280、240dp 窗口跟着收到 216、两态永远相等"。
连带一条纪律：**响应式规则不许只在伪报的大分辨率下看过**——那正好掩盖手机本档；
以后凡是改 `*MaxWidthDp` 这类按窗口宽走的判据，必须"原生档 + 伪报档"各拍一张。

### 9.9 第六批（2026-10-04 凌晨）——找券三版落地，以及"控制面接手"抓出的两条真缺陷

四路并行（core / eval / ui / ai-policy）全部收口。**分支不是版本**，版本号等用户定。

**一、V1 理解层的形状（`com.pricelens.coupon`）**
- `Extraction.coupons: List<CouponSlot>` 与 `Extraction.price: PriceSlots` **分属两个类型** ——
  "到手价被当成券面额"这类错从类型上不可能再发生，这是治"金额槽位混淆"的正解，
  比再加十条词表都管用。
- `AmountRole.of` 只看**数字之前、离数字最近**的词，同下标取长词（`无门槛` 压 `门槛`）；
  判不出返回 null，**绝不默认 DISCOUNT**。
- 状态/范围按词表判，判不出是 UNKNOWN（不许默认 CLAIMABLE / SHOP）；
  优先级把强信号（售罄/过期）排在弱信号（`立即领`）之前。
- 三入口产出同一类型，`nodePath` **只有 PAGE_NODE 入口非空** —— 这个不对称本身就是
  "三入口确实走同一条流水线"的反证材料。
- 词表全部可被远端规则包整体覆盖（含宿主前缀表 `platformPrefixes`）：
  接一个新电商宿主 = 推一条规则，不是发一次版。

**二、两棒子代理都在 150 轮上限被打断，控制面接手时抓出的不是"语法错"而是两条真缺陷**
| 缺陷 | 怎么暴露的 | 为什么它一直没被发现 |
|------|-----------|---------------------|
| `AmountRole.of` 不限量"角色词与数字之间隔了多远" ⇒ `…满199减20 券码：ABCD1234` 里的 1234 被 20 多字之前的 `减` 认领，**凭空多出一张 ¥1234 的券** | 我把 `slots.single()` 换成带消息的 `oneSlot()`，一次红就把两张券的字段打全了 | `single()` 只说 "List has more than one element"，看不出多出来的是什么；而多出来的券带着**正确的** scope/state，看起来像真券 |
| `CouponSlot` 没有 `sourceText` ⇒ "这条不对"导出写不出与 `tools/golden/coupons.jsonl` 同格式的 JSONL | 写 #56 的导出前先读 golden 格式，发现第一字段就是原文 | 理解层自己不需要原文也能跑；断的是**下游复盘能力**，不在同一层就看不见 |

**二、补的是词，不是连接字。** `实付` 本来就在 FINAL 词表里，卡住的是它和数字之间隔着 `低至`

**三、`折` 是 `%` 的同族，而这条 RED 是观测到的、不是推理出来的。** `低至` 进词表之后立刻跑真流水线：

### 9.25 第二十二批（2026-10-06 下午）——顺着 §9.24 七 那条线索，抓到 #73 实现里的一处真 bug

**一、根因：进详情页那一次"再搜一轮"把刚带上来的身份抹掉了。**

而 `SearchViewModel.search()` 里 #73 那一步原来是**无条件**的 `_detectedSignature.value = null`。
串起来就是：浮窗 CTA 好不容易把 `focus_signature` 带进 App

§9.24 那一轮"整条链走通、屏上只写『输入：关键词』"量的就是这件事；
当时我只记到"正例没拿到"，没追到根因，这一步是欠着的。

### 9.26 第二十三批（2026-10-06 傍晚）——§9.25 六 那条缺陷修掉了，但用的判据不是我当时写的那三条

**一、样本。**`shots/w-case1.png`（15:14，正例那四次里的第一次）详情页顶部：

```
十分满意的一次购物 刚开始在网上买电子产品 还有些忐忑不安 收到…
¥5,288 现价        还没有历史价
```

这一条**没有**树夹具。手上只有这张截图，样本串是截图里可见的那一段（末尾被我们自己的
`TextOverflow.Ellipsis` 截断，页面原文更长）。所以本批的钉子只能是**字符串级**的，
不像 §9.6 那批能拿真机 XML 端到端跑 —— 这条差别记在这里，别把单测绿当成"真机复验过"。

**二、我自己在 §9.25 六 写下的三条特征，两条是错的。**当时写的是
"评论行的特征：以「十分满意/收到」这类口语开头、无型号数字、长度偏长"。落地前逐条对：

1. **"以口语开头"** ⇒ 词表开放，钉不住下一条。评价的第一句可以是任何东西，
   收词就是玩打地鼠，而且收进来的词（"购物""收到"）在商品名里也不是零。
2. **"长度偏长"** ⇒ **方向反了**。这正是 §9.6 那次 `TITLE_MAX_LEN` 从 80 提到 220 学到的东西
   （真商品名实测 32/61/145/170 字）：用长度当质量判据，先被误杀的永远是商品名。
3. **"无型号数字"** ⇒ 这条留着当**边界**用，不当判据用（见下）。纯中文无数字的商品名真实存在
   （`五粮液 第八代 52度 浓香型白酒 500ml` 有数字，但 `LAN兰时光…` 那串里"数字"只是规格尾巴），
   拿它否决会直接踩到"读不出标题比显示错标题更糟"那条红线。

**三、实际用的判据：句式，不是词表。**商品名是**名词堆叠**，评价是**一句话**。
`PriceNodeMatcher.PROSE_FUNCTION_WORDS` 收了十个高频功能词（的/了/很/还/也/都/就/在/我/些），
命中 **≥2 个不同词** 就判"这是一句话，不是商品名"。阈值为什么是 2 而不是 1：
单个「的」在真实商品名里完全可能出现（`透气舒适的跑鞋`），散文式的多个不会。
样本串命中 的/在/还/些 = 4 个；七条真机商品名（下面第二点）全部命中 0 个。

先剥 `【…】` 徽章段再判，跟黑名单同一个口径（`BRACKET_BADGE` 上记着的那次教训）。

**四、闸的位置：`isPlausibleTitle`，不是 `isDisplayableTitle`。**这个选择有实际后果，不是风格：
`extractTitle` 三级里的第三级是"逐个候选过闸打分"（`NodeSnapshot.kt:245` 的 `continue`），
判据放在 `isPlausibleTitle` 才会让启发式**跳过**评论行、继续找同一棵树上的真商品名；
放在 `isDisplayableTitle` 的话，启发式仍然把评论行当最好的一份交出来，然后被整条闸滤成 null
—— 结果是这一页**彻底没标题**，而它本来是有标题可读的。`isDisplayableTitle` 内部调 `isPlausibleTitle`，
所以规则路径与 `SearchViewModel` 那道复用点自动一起受保护。

**五、positive control（必须全部保住，逐字取自六棵真机树）。**
`AccessibilityLabelTest.REAL_PRODUCT_NAMES` 七条，覆盖三种容易误杀的形态：
纯中文（`泸州老窖 国窖1573 52度 500ml`）、带逗号（`泸州老窖 窖龄30年，52度 500mL 6瓶 礼盒装`）、
带徽章段与零宽填充（`雷神 【白条24期免息】猎刃S英特尔酷睿i7…`）。
只断言"评论被拒"而不管住这些，等于把脏数据换成读不出标题。

**六、边界钉了一条反方向的。**`叠加以旧换新下单，可再减1964元` 只有一个「了」，
**不归这道闸管**，测试里显式断言它仍然过闸 —— 治它的是 §9.6 那套"规则标题与启发式标题用同一把尺
比分"。写出来是为了以后别把这道闸当万能黑名单，也为了让那条比分判据继续被单独钉着。

### 9.27 第二十四批（2026-10-06 傍晚）——迷你详情页为什么不弹浮窗：测到了，而且两个候选假设都不对

**一、这批改了什么"说法"，没改判据。**任务原本是在两个假设里选一个：
（甲）"没等到落定帧"——服务只看到页面加载中的帧；（乙）"判据另有拒绝"。
用 TEMP-PROBE2（`PriceMonitorService` 里那段不许提交的探针，打 `branch/nodes/yen/titles/TOP3/GATE`）
在真机上量了三次，结论是：**乙成立，但真正的原因不在乙这个词能装下的范围里**——
拒绝是真的，可这页**本来就不该被放行**。下面三、四是数据。

**二、三个假设，两个被推翻。**
1. §9.24 那条"规则页门 `.*ProductDetail.*` 大小写敏感挡了迷你页"——已被 `RealDumpMiniDetailTest` 推翻（记在 §9.24 八）。
2. "没等到落定帧"——不成立。落地后等了 14 秒再等 3 轮 6 秒，事件一直在来（`A11Y-EVT` 7~12 行、`root=true`），
   树也读得到（`nodes=1279`，快照上限是 `MAX_SNAPSHOT_NODES=4000`，没截断）。
3. "判据另有拒绝"——成立，而且能指到具体那一关（见下）。

**三、拒绝发生在哪一关。**同一页（`com.jd.lib.productdetailmini.PdMiniImmerseActivity`，
屏上是「嗯嗯狗子60cm仿真拉屎搞怪毛绒抱枕…」¥29.80）的完整探针行：

```
A11Y-MISS branch=NotProductPage nodes=1279 yen=28 titles=28
  longest=Apple【7天试用】Apple苹果15ProMax手机iPhone15pro全
  TOP3=y=-1 Apple【7天试用】Apple ; y=1920 vivoX500 Pro 12G ; y=1868 嗯嗯狗子60cm仿真拉屎搞怪毛绒
  GATE checkout=[] buy=[加入购物车按钮|加入购物车] buyNow=[] detail=[] titleNull=false priceNull=false
```

对着 `isProductPage` 五关逐条读：无结算否决 ✓、有购买动作 ✓、读得出价 ✓、读得出标题 ✓，
**死在最后一关**——既没有商详分区标记（`detail=[]`），也没有商详底栏专属动作（`buyNow=[]`）。

**四、为什么"放行"是错的方向（这才是本批真正的结论）。**两条独立观察：

1. **底栏不在服务读到的那棵树里。**同一页的 uiautomator 视角只有 19 个节点，但「立即购买」
   同时挂在 Button 的 `content-desc` 和 TextView 的 `text` 上；而服务那边 `buyNow=[]`。
   `subtreeTexts` 两个字段都收，所以不是"没读 contentDescription"——是**那个底栏根本不在
   `rootInActiveWindow` 这棵树上**（另一个窗口）。
2. **服务读到的那棵树是整条信息流，不是一件商品。**`TOP3` 是按长度排的前三条标题：
   最长的那条（Apple 15 ProMax 推荐位）**连 bounds 都是空的**（探针里 `y=-1`，

### 9.30 第二十七批（2026-10-06 深夜）——反例其实**造得出来**，钩子早就在；viewport 那一半被自己的测量否掉了

但"只能靠单测"错了 —— 注入钩子一直存在，而且它造的恰恰就是反例要的那一格：

### 9.31 第二十八批（2026-10-07）——2.8.0.2 发出去了；发版当天撞出一条"暖缓存必然假红"的 CI 缺陷

**一、按记忆里那条固定顺序走的**（`pricelens-release-cut-ordering`）：
①版本字段提交 → ②合 main 推双远端 → ③切 tag/release 触发 CI 签名构建 →
④下载产物核 sha256 + **签名指纹** + 包内版本 → ⑤传 Gitee `dist` 孤儿分支 → ⑥回填 `update.json`。
每一步的取证：

| 步 | 事实 |
|---|---|
| ① | `versionCode=23 versionName="2.8.0.2"` 在 HEAD 里；`git status` 只剩两处一贯不入库的 TEMP |
| ② | `main` 快进 60 个提交到 `952db35`，双远端都推上（`--ff-only`，无合并提交） |
| ③ | release `v2.8.0.2` 触发 run `37586324988`，Android job 8m53s 绿（含真 runner 上的全量 `test` + 找券门禁） |
| ④ | 产物 3,304,679 B，`sha256 d90bbdcd…fcb769` **与 GitHub 自己报的 digest 一致**；`aapt2` 读包内 `versionCode='23' versionName='2.8.0.2'`、内置规则 `"version": 4`（与 `rules/manifest.json` 记的 v4 与 sha256 逐字一致） |
| ⑤ | `dist` 分支**累加**提交（不 `git rm`，旧版直链继续有效），10 个包；双远端都推 |
| ⑥ | 两条直链先 curl 核对再发清单：Gitee raw 取回 3,304,679 B / `d90bbdcd…` **完全吻合**；然后才提交 `update.json` |

**签名身份是这次最该核的一条**：新包证书 `SHA-256 c759cbb8ca2bda75799d75336d615390ec5737d83cb588703bef09821205b5e0`
（DN `CN=wuliao00, OU=PriceLens`），与从 `dist` 下载回来的 **2.8.0.1** 逐字相同 ⇒ 老设备可覆盖安装、数据不丢。
这一步不能靠"应该是同一个 key 吧"，`apksigner verify --print-certs` 两遍即可。
顺手也验了记忆里的另一条：2.8.0.1 的 `update.json` 记录的 sha256 与实际下载到的**一致**，
说明这条链子以前没坏。

**二、本机出不了正式包**（下次别再假设能）。`docs/DEVELOPMENT.md` 的发布段写的是
"本机 `local.properties` 四行指向 `~/.android/PriceLens-release.keystore`"，但这台机器上
**那把钥匙不存在**——`.android/` 里只有 `debug.keystore`。所以签名只能走 CI 的
`PRICLENS_STORE_B64` 那一路（四个 secret 都在，2026-10-01 配的，`HAS_RELEASE_KEYS=true`）。
**绝不能用 debug.keystore 顶**：文档里写着 v2.7.0 起正式包换成了独立密钥，
debug 签名既带 `android:debuggable`、又与线上包签名不同，装上去就是"用户只能卸载重装"。

**三、发版当天撞出的 CI 缺陷：暖缓存必然假红。**同一棵树，release 事件那次 8m53s **绿**，
紧接着推 main 那次 59 秒 **红**，报的是"预测文件没生成"。根因：

```
> Task :app:testDebugUnitTest FROM-CACHE
BUILD SUCCESSFUL in 40s
```

Gradle 构建缓存命中时只恢复任务**已声明的输出**，而 `app/build/coupon-predictions.jsonl`
是 `CouponGoldenPredictionTest` 自己写进 build 目录的副产物、**没有被声明** ⇒
暖缓存那一轮它压根不存在，于是门禁的"缺文件即红"守卫炸了。
守卫本身是对的（宁可红，也不要 `if: 文件存在才跑` 那种静默跳过），
缺的是把两件事分开：**"没测"** 和 **"测过但产物没落盘"**。
修法（`26bd08d`）：缺文件时先 `./gradlew :app:testDebugUnitTest --tests "*CouponGoldenPredictionTest*" --rerun`
强制执行那个测试，再判 —— 既不假绿也不假红。

**四、两条与本批有关但没动的**：① GitHub 的 release 直链在这台机器上 `curl` 返回 000
（与推 GitHub 时偶发的 `Failed to connect` 同源），但资产存在（`gh` API 确认 3,304,679 B）——
客户端主源是 Gitee，且清单里 Gitee 排第一，所以不影响用户；② tag 只在 GitHub，
与 `v2.8.0.1` 的既有状态一致（Gitee 上一个 tag 都没有），所以没往 Gitee 补推。


### 9.32 第二十九批（2026-10-07）——#73 结项：两条腿都有真机证据了

**一、先说清"关在哪儿"。**用户让去关 #73，但查下来的事实是：
GitHub 仓库 `wuliao00/PriceLens` **issue 总数为 0**（含已关闭），PR 编号最大到 30；
Gitee 侧 `GET /repos/wuliao11541/PriceLens/issues?state=all` 返回 `[]`，
`/issues/73` 返回 `{"message":"Issue"}`（取不到）。
⇒ **#73 不是一个可关闭的 issue 对象**，它是规划文档里的编号（本文里第一次出现在 §9.19 附近：
"#73（商品身份约束）与 #70（剪贴板正样本）都要把这条当成前提"）。
所以结项只能落在**这份账本**里；如果它在别处（外部看板 / 私人清单）有一条记录，
需要用户自己去勾，或告诉我在哪，我再补一句验收结论。

**二、#73 要的是什么。**一句话：**页面树那一路的输入必须属于当前这件商品**——
一棵树只能用一次，且必须与本次商品上下文的身份签名同源，
否则就会重现"看 A 商品的页、券行挂在 A 上、而出处行写着『这一页的节点文案』"那种指错了的假话
（#72 放宽了树的生命周期，正是这条约束必须存在的原因）。

**三、两条腿的证据。**

| | 怎么验的 | 结果 |
|---|---|---|
| **正例**（该采纳时采纳） | 有机路：京东商详 → 浮窗 → 「识别到标题 · 点击在 App 内搜索」→ 详情页找券段 | 出处行显示「输入：**这一页的节点文案** · 26 秒前 + 关键词」，本轮在 2026-10-06/07 独立复现 6 次（最后一次截图 `n107-coupon.png`，商品 OPPO Find X9 ¥3,599） |
| **反例**（不该采纳时剔除） | 同一格状态下，用 `app/src/debug` 的注入钩子塞进一棵**更新的、签名不等**的树：`am broadcast … --es page_capture "满999减500；反例专用注入券ABC"` | 出处行退化为「输入：**关键词**」，注入那张券**没有**出现在任何一行（截图对照 `n107-coupon.png` vs `n107-injected.png`）。注入发生在检测后 25 秒，远在 120 秒窗口内 ⇒ "消失"只可能来自签名不等，不能赖树过期 |

**四、这条反例为什么以前"造不出来"，以及我更正了什么。**
§9.25 五 记的是"反例真机上不可构造，只能靠单测与代码走查"。那半句只对**有机路径**成立
（App 活着时当场采纳每一次新检测 ⇒ 签名与树永远同步，两者互相抵消）。
注入这条路我当时一起否了，而 `PageCapture.plan` 与 `LlmProbeReceiver` 两处注释也写着
"这一路只能用真机验、注入验不了"——那**只说中了正例**：注入造不出身份归属，
但反例要的恰恰是"签名不等"，注入是唯一造得出的办法。两处注释已在 §9.30 改准。

**五、实现落点**（给以后读代码的人，不用重新找）：
`DetectionContext.survivesSearch`（换词/换候选就作废身份，修的是"进详情页那次重搜把身份抹掉"）、
`SearchViewModel._detectedSignature`（身份的唯一持有者）、
`LocalCouponInputPlanner.plan(capture, …, currentSignature)`（**闸本体**：
`currentSignature != null && capture.signature == currentSignature` 才放 PAGE_TREE 进来）、
`PageCapture.publish`（只在 `emitDetection` 里发布，所以树与签名同源）。
测试：`DetectionContextTest`、`LocalCouponInputPlanner` 的"签名不等或为 null 就不进清单"那组。

**六、#73 结项。** 两条判据（采纳 / 剔除）都在真机上取到证据，实现与测试齐备，
随 **v2.8.0.2** 发布（`versionCode=23`，`update.json` 已生效）。
仍开着的不是 #73，而是两件它引出来的、各自有独立编号的事：
迷你详情页不弹浮窗（§9.27 判为**正确行为**，要改需先解决"一屏多商品"）、
以及推荐位/广告位文本漂进标题的结构性修法（§9.29 落了"必须有位置"那一半，
视口过滤与多窗口取树按 §9.31 的测量结果暂不做）。

### 9.34 第三十一批（2026-10-07 夜）——把**发出去的那份**装回真机跑通了

**一、要关的缺口。**§9.33 四 留了一句"没做成"：本轮所有真机验证跑的都是 debug `.dev` 包，
而用户拿到的是 R8 混淆 + 资源收缩的 release 包。用户点头清掉了分身空间那枚 debug 签名的
`com.pricelens` 2.7.0（**它的本机数据随之清除**，这是那次卸载的代价，已记在这里），
装上 `dist` 直链取回的 2.8.0.2（sha256 与清单一致），跑 `step109.py`：

| 判据 | 结果 |
|---|---|
| 启动不崩 | `com.pricelens` 进程存活，`MainActivity` 到前台 |
| 无障碍服务能绑上（混淆会改掉 manifest 类名 ⇒ 这是 R8 最典型的死法） | `dumpsys accessibility` 计数 = 1 |
| 检测链跑通 | 京东搜索 → `ProductListActivity` → 商详 → **浮窗窗口出现**（帧 280,284,1048,500） |
| 内容对不对 | 面板标题 `自营拍拍二手【8新·C】Apple 苹果 iPhone 15 128G 黄色 国行 全网通`，与页面真实商品名逐字一致；券后价 ¥1,909 与底栏一致；两个 CTA 正常 |
| 我们进程的崩溃 | `FATAL` 行数 = **0** |

⇒ **"测的那份 ≠ 发的那份"这条风险本次关闭**：release 与 debug 两份制品在这台机上行为一致。

**二、过程里最重要的发现不是产品，是量具。**第一版工单 `step108.py` 报
"崩溃 108 行、浮窗 FAIL"，看着像 release 包炸了。逐条看栈才认出来：

```
java.lang.IllegalStateException: UiAutomationService … already registered!
    at …IAccessibilityManager$Stub$Proxy.registerUiTestAutomationService
```

`registerUiTestAutomationService` 是 **`uiautomator` 自己**调的接口——
PriceLens 是 AccessibilityService，从来不碰它。所以那 108 行是**我的量具在连续
`uiautomator dump` 时自己撞死**（前一个会话没释放，后一个注册就崩），
不是被测包。更糟的是它**之后永久坏掉**：dump 稳定返回 0 字节，
关掉无障碍服务不恢复、杀掉 `com.pricelens:shell` 持有者也不恢复（槽位卡在 system_server，
只有重启手机能放掉）。于是那一版报的"浮窗 FAIL"是**量具失效导致根本没跑到那一步**。

处理：`step109.py` 改成**完全不依赖 uiautomator** —— 页面身份用 `dumpsys activity`、
浮窗用 `dumpsys window`、导航用坐标。换路子之后一次跑通，全绿。

**三、这是本轮第三条"量具安静地给一个假答案"，三条同族，值得并排记：**

| 假答案 | 真因 | 正确的量法 |
|---|---|---|
| "0 条命中"（§9.28 三） | 命中日志是 `LogT.i`，这台机全局等级只出 E | 用浮窗窗口或 App 私有库，不用日志 |
| "门禁红"（§9.31 三） | Gradle 暖缓存只恢复**已声明的输出**，副产物没落盘 | 缺产物先强制执行那个测试 |
| "正式版没装"（§9.33 五） | `pm list packages` 不带 `-u` 只列当前用户 | `pm list packages -u` + `dumpsys package` 看 User 行 |
| "release 包炸了"（本批） | uiautomator 自己的 UiAutomation 注册冲突 | 按**进程归属**过滤崩溃；能不用 uiautomator 就不用 |

共同形状是同一个：**工具的默认作用域/生命周期会安静地返回一个空值，而空值看起来像结论。**
以后凡是"读到 0 条 / 空 / 没命中"，先问一句这是被测对象的性质，还是量具的性质。

**四、设备现状（下次接手要知道）。**`com.pricelens` = 正式签名的 **2.8.0.2**（真机验过的那份），
分身空间里那枚 debug 2.7.0 已按用户同意卸载；`.dev`（探针包）仍在；
无障碍、悬浮窗权限均已按 `a11y-baseline-v2156a.txt` 复位（services=null / a11y=0 / 两个包都 ignore）。
`uiautomator dump` 在这台机上目前仍是坏的，**重启手机**才恢复。
